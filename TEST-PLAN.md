# Quota Guard — универсальный план проверки

Статус: **утверждённый универсальный план после приёмки**. Перечислены воспроизводимые проверки актуального поведения без привязки к историческим значениям квот или числу токенов; конкретный прогон фиксируется отдельно в протоколе раздела 10.

## 1. Назначение и область

План применяется после изменений статистики, диагностики, квот, RPC или Desktop GUI. Полный прогон обязателен перед публикацией; для точечного исправления дополнительно выполняются все связанные сценарии и финальная сборка.

Проверяются:

- квоты ChatGPT, Kimi Ultra и Kimi Ultra Aprobo раздельно;
- статистика «Сегодня» / «7 дней» и сравнение с базой;
- диагностика холодных шагов, проектов, времени и истории;
- Desktop GUI, RPC, настройки и ручное управление;
- отказоустойчивость, конфиденциальность и инвариант «только предупреждения».

Не проверяются платными генерациями и не требуют реальных изменений текущей модели. Не использовать содержимое диалогов, ключи, токены авторизации или платёжные данные в доказательствах.

## 2. Роли и независимость

1. Разработчик выполняет scoped-проверки своего изменения.
2. Независимый QA, не писавший этот код, воспроизводит тест-план без правок и возвращает доказательства.
3. Orchestrator проверяет ключевые выводы по источникам, сам выполняет Desktop click-through и принимает или отклоняет результат.

Успешная сборка или отчёт субагента сами по себе не являются приёмкой.

## 3. Подготовка и доказательства

- Зафиксировать версию, изменённые файлы, исходные настройки и состояние панели.
- Выполнять из каталога плагина: `npm test`, `npm run check`, `npm run build`.
- Для RPC сохранять HTTP status, метод, период и только необходимые агрегированные поля ответа.
- Для Desktop сохранять скриншоты day/week и проблемных состояний; не включать секреты и приватный текст.
- Фиксировать точную команду, exit code и релевантный фрагмент ошибки. Скрывать credentials.
- После любой правке повторить затронутые сценарии; прежние доказательства считаются устаревшими для изменённого кода.

## 5. Диапазоны, токены и сравнения

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| STAT-01 | День и его база | Current: локальная полночь–now. Baseline: предыдущие календарные сутки до того же времени. Границы half-open. |
| STAT-02 | Неделя и её база | Current: now−7×24 ч–now. Baseline: предшествующие 7×24 ч. Нет перекрытия диапазонов. |
| STAT-03 | DST/смена часового пояса | Календарный день не заменён ошибочно фиксированными 24 ч; week остаётся скользящими 7×24 ч. |
| STAT-04 | Состав токенов | Полный вход = U+R+W; полный выход = output+reasoning. Reasoning не складывается повторно. |
| STAT-05 | KPI кэша | ReadShare = R/(U+R+W); амортизация = R/W. Рядом видны числитель и знаменатель. |
| STAT-06 | Нулевой знаменатель | Значение `null` / «—», не 0, NaN или Infinity. |
| STAT-07 | Отсутствующее поле против нуля | Missing остаётся неизвестным; реальный 0 не превращается в missing. |
| STAT-08 | Смена вида второй KPI | При разных `secondKpi.kind` сравнение недоступно; нет вычитания разных метрик. |
| STAT-09 | Current успешен, baseline пуст | Current отображается; все сравнения нейтрально серые с причиной «нет базы», без выдуманного green/red. |
| STAT-10 | Current пуст, baseline успешен | Явное пустое текущее состояние; база не подменяет текущие значения. |
| STAT-11 | Один из запросов упал | Доступная половина сохраняется; недоступная помечается неизвестной, не нулевой. При current unavailable нет сводки «0 шагов · 0 токенов». |
| STAT-12 | Модели и варианты | Варианты объединяются только внутри provider+model; подписка и платный API не смешиваются. |
| STAT-13 | Стоимость | План — «по плану», Ollama — «локально», платный API — числовая стоимость; нет ложного суммирования. Исторический OpenAI auth-класс — документированное ограничение, если источник не содержит прошлый способ оплаты. |
| STAT-14 | Независимые компоненты | Missing/cross-kind cache или reuse не отключает вычислимый input; gray назначается только затронутой компоненте. |
| STAT-15 | Смешанные модели | Red input у модели A и amber cache у модели B дают aggregate input red и cache amber, без ложного green от одной выбранной модели. |
| STAT-16 | Partial model tokens | Неизвестные cache/output/reasoning не становятся известными нулями; затронутые KPI/assessment остаются null/gray. |

## 7. Desktop click-through — обязателен для приёмщика

Каждый пункт выполняется на фактическом Desktop после последней сборки. После hot reload закрыть и заново открыть панель, чтобы проверялся новый GUI-бандл, а не старый mounted instance; снимок до remount не является доказательством исправления.

1. Открыть панель через плитку и через боковую область; свернуть/развернуть её.
2. Нажать «Обновить»; дождаться завершения и проверить отсутствие зависшего loading.
3. Раскрыть «Статистика и эффективность»; проверить lazy load и текущий период.
4. Переключить «Сегодня» → «7 дней» → «Сегодня»; сверить содержимое с RPC соответствующего периода.
5. Быстро переключить периоды несколько раз; поздний ответ не должен перезаписать выбранный период.
6. Проверить обе KPI, вход, выход, baseline, модели и сравнение с базой в day и week. При пустой базе объяснение находится сразу под итогом, не дублируется после KPI; текущие значения остаются видимыми.
7. Проверить видимые области оценки: цвета KPI/входа — по худшей сопоставимой модели, числа — по итогу; выход — по итогу и только объём. Смешанный fixture не даёт ложный green.
8. Раскрыть/закрыть «Как считается» и «По моделям и сравнение с базой»; правила и пороги доступны без hover, данные и скролл не ломаются.
9. Раскрыть «Диагностику»; проверить общий период, вкладки «Холодные», «Проекты», «Время».
10. Раскрыть проекты → сеансы → субагенты/модели и детали холодных шагов; проверить длинные списки и отсутствие двойного учёта.
11. Проверить сворачивание/разворачивание, прокрутку всей панели и внутренних ограниченных списков.
12. Проверить верхние карточки: квоты, кредиты, reset, скорость, предупреждения и компактность при широкой/узкой панели.
13. Убедиться в отсутствии «не число», `NaN`, `undefined`, необъяснённого «недоступна», пустых badge и обрезанных кнопок.
14. Проверить loading/error/retry: `aria-live`/`role=status`, рабочая кнопка «Повторить», current unavailable не отображается нулями.
15. Проверить клавиатурный фокус, Enter/Space на интерактивных элементах, `role=progressbar` и aria-значения; контраст мелкого текста ≥4.5:1 в обеих темах.
16. Проверить длинные названия моделей и формулы в узкой панели: перенос без горизонтального overflow.
17. Проверить заголовок/подсказки больших чисел: сокращение не скрывает точное значение.

### Состояния, которые нужно получить fixtures/mocks при отсутствии в живых данных

- loading, ошибка RPC, повторная успешная загрузка;
- пустой current, пустой baseline, частичные/nullable-поля;
- green/amber/red/gray для каждого типа оценки;
- активный шаг, последний шаг, отсутствие измерений;
- неактивные провайдеры, истёкшие данные, исчерпанный лимит.

Живой скриншот одного состояния не заменяет проверку остальных.

## 8. Управление и безопасность

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| CTRL-01 | Общий мониторинг off/on | Опрос и предупреждения останавливаются/возобновляются; исходное значение восстановлено после теста. |
| CTRL-02 | Per-provider monitoring | Меняется только выбранный провайдер; две Kimi не связаны; исходные значения восстановлены. |
| CTRL-03 | Пороги/интервал | Валидные значения сохраняются, невалидные не повреждают настройки; исходные значения восстановлены. |
| CTRL-04 | Ручная смена модели | Только mock или изолированная тестовая сессия; текущая пользовательская модель не меняется без отдельного разрешения. |
| SAFE-01 | Автоматические действия | `automaticActions.interrupt=false`, `switchModel=false`; нет автоматической остановки или смены модели. |
| SAFE-02 | Платные вызовы | Тесты статистики и GUI не создают generation-запросы. |
| SEC-01 | RPC/logs/UI | Нет API keys, OAuth tokens, cookies, текстов диалогов или платёжных реквизитов. |
| SEC-02 | Diagnostics JSONL | Только разрешённые технические поля; retention 7 дней и cap 10 МБ не нарушены. |
| SEC-03 | Git | Аудит tracked diff и истории; секреты и локальные приватные данные не публикуются. |

## 9. Критерии завершения

Работа принимается только когда:

- нет открытых blocker/critical/high дефектов в согласованной области;
- независимый QA завершил прогон без правок и предоставил доказательства;
- Orchestrator сам выполнил Desktop click-through для day и week после последних правок;
- связанные автоматические тесты, `check` и `build` успешны;
- ограничения и невозможные в живой среде состояния явно покрыты fixtures/mocks;
- документация соответствует фактическому поведению;
- финальный diff не содержит out-of-scope изменений и секретов.

Если проверка не выполнена, она отмечается **«не проверено»**, а не «пройдено».

## 10. Протокол приёмки

Для каждого прогона заполнить:

```text
Дата / версия / commit:
Изменённые файлы:
Команды и exit codes:
RPC day/week:
Desktop day/week:
Независимый QA:
Скриншоты/artefacts:
Найденные дефекты и исправления:
Не проверено / ограничения:
Итог: ACCEPTED / REJECTED
```
